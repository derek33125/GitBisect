从 crash report 出发，能走到 gt commit 吗？

每个案例都以一份 crash report 为唯一起点。下面统计的是：把 crash 里能直接读到的东西 （断言文件、栈上符号、正在运行的 pass）拿去和 ground-truth commit 的改动文件做匹配， 最强的那条线索落在哪一层。层级越靠后，说明纯文本检索越无能为力、越必须靠因果推理或实际编译验证。

逐例对照

方法说明

  • 文件级：crash 里出现的源文件路径，本身就在 commit 改动列表里 —— 直接 grep 文件名即可锁定。
  • 符号级：断言所在文件没被改，但调用栈上某个类/函数名对应到改动文件（如 AsmPrinter::emitXRayTable → AsmPrinter.cpp）。
  • Pass 名级：崩溃点与改动完全无关，只有 Running pass 里的 pass 名能对上文件名（如 simple-loop-unswitch → SimpleLoopUnswitch.cpp）。
  • 模块级：只共享目录层级，需要再读 diff 才能判断语义关联。
  • 仅先验目录：只有现有系统那份 high-risk 目录先验能覆盖到它，crash 文本本身捞不到。
  • 文本不可达：crash 与 commit 无任何词面重叠，只能靠 bisect 编译验证。

一句话

崩溃的地方，
通常不是出错的地方。

崩溃报告点名的那个文件，往往只是最先察觉异常的地方，而不是把状态弄坏的地方。 定位之所以难，很大程度上就难在这一步错位上；我们要做的，是绕过它。

错位是怎么来的

于是换一个问法

既然崩溃现场问不出肇事者，就不再问「崩溃现场长什么样」，而是问 「谁有可能影响到这个被违反的约定」。 这个问题不需要猜，它是一个依赖关系问题：能破坏某个组件约定的代码，必然与该组件存在依赖关系， 而依赖关系在 bad 版本的源码树里查得到。于是定位就从「比对文字」变成了「查引用」。

具体做四件事

前三件构成三条互不重叠的证据通路，各自回答一个不同的问题，最后合成一个排序； 第四件与排序无关，省的是每验证一次所花的时间。

这三层不是三份人工 profile。 ① 崩溃直接信号取自 bad-endpoint artifact；② 推导目录由这些信号在 bad tree 中机械映射得到；③ 锚点、消息、流水线与阶段仍只由 artifact、reproducer、 仓库注册表、源码引用和 commit 元数据自动导出。旧分析曾讨论的「issue 正文 LLM fallback」不进入最终 CEG 的召回或排序。

另有一条 看起来像 2–4 步大胜、其实不能当成功：adjacent-parent 验证只证明「这个候选 bad 且它的 Git parent good」。 谓词不是单一的 good … bad 时，这条局部跃迁不必等于台账 first-bad。 已核对：pr121365 是同一 patch 的 land → revert → re-commit； pr167514 是 Git 更早的第一次 onset 之后又出现一段 good，CEG 锁在第二次 onset。 详写在下面「相邻 SHA 为什么不同」。

在线策略事实（用来解释上面三条，不是新实验）：程序先验是主召回器；人工 keywords / relevant_paths / high_risk_paths 不参与排序。 直探：frontier rank-1 + invariant-break / precondition-violation + confidence ≥ 0.95，再验证真实 parent。 低分 commit 保留概率地板，不会因为没撞上崩溃文件就被删掉。

于是具体做四件事（现行 CEG）

前三件构成互不重叠的证据通路，第四件只管验证成本。

1崩溃直接信号

bad-endpoint artifact 里的断言文件、栈符号、Running pass。

2推导目录

这些信号在 bad tree 上映射出的组件目录与后端。

3锚点 · 消息 · 流水线 · 阶段

源码引用、commit message（只用 crash/reproducer 词）、pass 前驱、编译阶段。合成全区间程序先验。

4frontier 因果 + runner

模型只比较可见 patch 是否连得上崩溃契约；边界必须「候选 bad + 真实 parent good」。

合并顺序：全区间程序证据评分 → 有支撑位的 12 人 frontier → LLM 批内 ordinal → 保持总质量的局部重排 → 信息增益与可构建性 → 真实构建。

接到在线搜索里：LLM 环节怎么改

「技术细节」页讲的是离线怎么把候选排出次序，这一页讲的是这套先验怎么接进真实的模型引导二分。 当前实现遵循一条职责边界：能确定计算的事实由程序完成，模型只判断真实 patch 是否存在通向崩溃契约的因果桥。程序先验覆盖整个未决区间， 有界 frontier 控制模型预算，ordinal 结果只在 frontier 内保持总质量地重排， 最终边界仍由 runner 的 bad-candidate / good-parent 组合确认。 下面依次给出完整数据流、安全契约、初步在线结果，以及从旧 prompt 收敛到当前职责划分的过程。

最终方法：Causal Evidence-Guided Bisect（CEG-Bisect）

现有的确定性事实因果排序管线已经会为一小批候选检索真实 hunk、 仓库事实与断言契约，再让模型比较哪个 patch 更可能破坏该契约；它的短板是， 这批候选仍由人工编写的关键词与路径权重选出。 CEG-Bisect 补上前半段：在任何构建之前，对未决区间内每个提交打一个程序证据分。 分数只来自当时可见的崩溃原文、reproducer、bad 版本源码树和提交元数据， 不读取正确答案，也不删除低分提交。这个全区间分布叫程序证据先验； 它决定模型先看谁，原有因果排序负责判断这些候选的 patch 是否真的连得上崩溃机制。

层确定性事实因果排序全区间程序分析CEG-Bisect
全区间初排 人工 keywords / relevant paths / high-risk paths 的固定权重 从 artifact、reproducer、bad tree 推导信号，按区间覆盖率的自信息排序全部 commit 程序证据先验作主召回器；人工 profile 的关键词与路径不参与召回或排序
模型看到谁 人工启发式的 top-12 不需要模型即可给出全区间名次 先验高分项 + 概率中点 / 时间中点；可构建性不占候选名额
模型做什么 读真实 hunk 与仓库事实，作批内 ordinal causal judgment 程序负责事实提取，不应让模型重做 grep 与覆盖率统计 只比较可见 patch，判断谁能沿调用或依赖关系破坏崩溃契约
进入在线搜索 模型分与未进模型的启发式分处在不同尺度 静态排序本身不决定下一个构建点 模型只在候选小批次内重分配原有概率，再按信息增益与可构建性选探针
“人工 profile 不参与”的准确范围。 CEG 仍需从 issue 配置读取 good_commit、bad_commit 和 runner 来定义评测区间与执行命令；这些是运行配置，不是定位证据。 最终排序不读取人工撰写的 title / summary / keywords / relevant_paths / high_risk_paths。它的三级程序证据全部自动产生： ① 崩溃直接信号（栈符号、pass 名、崩溃文件）； ② + 推导目录（断言/符号目录与 target triple 对应后端）； ③ + 锚点 · 消息 · 流水线 · 阶段（bad tree 源码用量、 只用 crash/reproducer 词匹配的 commit message、pass 注册表与前驱、 编译阶段字符串和 tool/module/target 路径）。多层代码分析与“无人工定位先验” 并不矛盾：区别在于证据是否由当前 bad endpoint 和仓库确定性导出。
合并顺序： 全区间程序证据评分 → 有支撑位的候选小批次 → LLM 批内因果排序 → 保持总概率的局部重排 → 可构建性 + 信息增益 → 真实构建反馈。 对 frontier F，令其原总质量 M_F = Σ p_i，重排后 p'_i = M_F · p_i·w(rank_i) / Σ_F p_j·w(rank_j)； frontier 外 p'_i = p_i。这样不会把两套不可比的绝对分混在一起。

            新增方法节草稿：Causal Evidence-Guided Bisect（CEG-Bisect）

            动机与缺口 确定性事实因果排序器已将结构化崩溃证据、仓库事实和锚点相关 hunk 交给模型， 并把模型任务限制为批内因果排序； 然而，进入该批次的候选仍由人工设计的关键词/路径启发式选出。 因而它改善了「如何判断一个已召回候选」，却没有解决「全区间哪些候选能够被召回」。

            程序先验 我们只使用失效时可获得的 crash artifact、reproducer、二分区间与 bad 版本源码树， 从断言、栈符号、pass / phase、程序目录和依赖使用关系构造信号集合。 每条信号按其在当前区间内的覆盖率赋予自信息权重；细粒度信号在同一观测组内取最大值、跨组求和。 所有 commit 保留非零质量，因此该先验改变验证顺序而不排除候选。

            有界 ordinal 重排 在线阶段由程序证据先验负责全区间召回，确定性事实因果排序器只在有界候选小批次内判断候选 patch 是否存在到崩溃契约的可见因果桥。模型输出被解释为局部乘法因子，而不是新的绝对分； frontier 的总先验质量在重排前后保持不变，非 frontier 质量不变。 buildability 与真实 good / bad / skip 观测随后只参与探针效用和区间更新。

            可审计性 这种分工把确定性程序事实、模型的代码语义判断和真实执行反馈拆成三个可独立消融的层， 同时避免 heuristic 分数与 LLM 分数混用、checker/producer 错位以及候选硬裁剪。

            论文口径：可以报告两例冻结配置的初步在线结果： pr204559 为 7 次 runner build（确定性事实 8、BCR 10）， pr201444 为 9 次（确定性事实 11、BCR 10），两例边界都正确且无 cache / skip。 但在完成全部 paired scoped-10 lane 之前，不能声称总体构建次数已经下降。 Master-50 参与了方法形成，只能作回顾性泛化。
