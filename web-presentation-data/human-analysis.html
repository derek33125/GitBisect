01 / What the study found

Crash evidence is a prior, not a first-bad locator

Across the scoped ten, the retrospective analysis classified six first-bad changes as direct mechanism matches and four as indirect enablers. The crash site is often a checker rather than the producer, so the method must preserve every unresolved commit and use crash evidence to improve retrieval rather than as a hard candidate filter.

02 / What changed in BCR

V15 sends deterministic facts and real hunks to one ordinal judge

Original BCR retrieves parent-diff evidence, asks one LLM to compress it, then asks a second LLM for an absolute semantic score. V15 keeps the top-k12 frontier and runner update, but moves fact construction into code and removes that extract-then-score pair: one ordinal LLM call judges failure mechanism from selected real hunks plus structured crash and repository facts. V16 retains that loop, adds artifact-complete lookup for future master-50 runs, and supplies five parent contexts per candidate.

BCR V15 / deterministic facts

Use the known crash contract before the first build

Code parses the bad-endpoint crash artifact and ranks parent-diff hunks with stack business symbols, pass tokens, assertion terms, signed crash-file frequency, dependency/API use, assertion-contract context, destruction surface, and explicit contact-path or no-contact facts. A rare crash file is treated as a likely checker. These are weights, never eligibility filters.

# original BCR: two LLM calls
evidence = causal_LLM_extract(selected_hunks, context)
semantic = LLM_absolute_score(evidence, issue_summary)

# V15: code builds facts; one LLM judges mechanism
facts = crash_contract + checker_polarity + dependency_use
facts += invariant_context + destruction_surface + contact_path
ordinal = LLM_rank_mechanism(selected_real_hunks, facts)
posterior = calibrate_ordinal_in_code(ordinal, unresolved)
candidate = calibrated_posterior_select(posterior, unresolved)
Method contract / evidence and leakage

Human-guided BCR is crash-informed, not first-bad-informed

The phrase "human-guided" describes where the extra retrieval signals came from, not that a human supplied the answer. The important boundary is whether the run receives information derived from the unknown first-bad commit. Parsing the crash artifact at runtime is valid: a bisect starts with a known bad endpoint and can inspect its failure report. Supplying the first-bad SHA, its patch, or an anchor selected after seeing ground truth is answer leakage.

Original BCR / causal-llm

Issue profile plus candidate parent-diff evidence

For each unresolved interval, it ranks changed files and hunks using the issue profile, relevant and high-risk paths, and issue keywords. It retrieves bounded function context, asks one causal extractor to summarize the candidate change, and sends that evidence to the shared calibrated-posterior scorer.

issue profile + parent diff -> file/hunk ranking -> function context -> causal extraction -> posterior scoring
Input
No crash-artifact signal in the production retrieval policy.

Historical Human-guided BCR / causal-llm-human

Original loop plus step-zero crash signals

It parses the supplied crash or assertion artifact before the first probe and adds source paths, business stack symbols, pass tokens, and assertion query terms to file and hunk ranking. The historical pilot used human-study-v1 normalization, which was designed retrospectively from this scoped study.

crash artifact at runtime -> normalized signals -> parent-diff ranking -> causal extraction -> posterior scoring
Input
Known bad-endpoint artifact; no first-bad SHA or first-bad patch.
Status
Not direct answer leakage, but study-tuned and not a clean deployable baseline.
Human-study BCR V15 / causal-llm-deterministic-facts

Runtime crash facts plus one ordinal mechanism judgment

It uses the general runtime parser, then has deterministic code rank crash-aware hunks and compute checker polarity, assertion-contract, destruction-surface, dependency-use, and contact-path facts. Selected real hunks and those facts go directly to one ordinal rank/mechanism/confidence call; code calibrates the result into the existing posterior.

parse artifact -> deterministic hunk/fact construction -> one ordinal mechanism call -> code calibration -> posterior scoring
Input
Runtime crash artifact and known bad endpoint only; no study-selected anchor map, first-bad SHA, or first-bad patch.
Status
No first-bad leakage
V16 window BCR / causal-llm-deterministic-facts-artifact

V15 loop with artifact-complete lookup and five parent diffs

V16 keeps V15's deterministic fact construction, single ordinal mechanism call, and calibrated posterior. It first discovers packaged crash-assertion.err artifacts for broader master-50 coverage, then supplies the candidate diff plus five first-parent contexts. Compatibility compiler settings are execution plumbing only and do not change retrieval or scoring.

artifact lookup -> deterministic facts + candidate/5-parent diffs -> one ordinal mechanism call -> code calibration
Input
Runtime crash artifact and known bad endpoint only; no first-bad SHA, patch, or ground-truth-selected anchor.
Status
No first-bad leakage
How to read the claim: runtime parsing is not the leak. The historical method is "not direct answer leakage" because it does not receive the first-bad identity, but its fixed normalization was shaped after reviewing this cohort, so its result is reported as a historical study-tuned comparison. V15 derives facts from the artifact and repository at runtime, does not use a ground-truth-selected per-issue signal, and never treats those facts as a build observation.
Separate diagnostic methods: the answer-informed pool/frontier methods (causal-llm-human-pool, human-prior, and human-frontier) and oracle heuristic variants use retrospective signal mappings or first-bad-derived information. They must not be grouped with causal-llm-human or V15 when claiming a non-leaking baseline.

04 / Heuristic scoring ablation

Which tuned-heuristic factors carry the ranking signal?

The baseline is a deterministic semantic score followed by calibrated-posterior selection. Each ablation removes exactly one factor; endpoints, runner, candidate interval, posterior policy, and all remaining factors stay fixed. Skip-capped and running histories stay visible but never enter the clean aggregate.

Tuned baseline

Semantic relevance, buildability, and observed feedback

Issue-specific crash terms and path priors generate semantic relevance. Build-success probability prevents selection of candidates likely to fail for unrelated configuration reasons. Runner observations then reweight later candidates, while only a successful reproduction contracts the actual good/bad interval.
